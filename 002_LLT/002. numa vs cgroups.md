# NUMA and cgroups — Interview Reference

Covers NUMA architecture, CPU/process pinning, and cgroups (v1/v2) fundamentals — with the practical connection between the two for tuning containerized or latency-sensitive workloads on bare metal.

---

## 1. NUMA (Non-Uniform Memory Access)

### What it is

On modern multi-socket servers, each CPU socket has its own bank of memory physically attached to it, but all sockets can technically access all memory in the system through an interconnect (Intel's QPI/UPI, AMD's Infinity Fabric). "Non-uniform" means access time isn't the same for all memory — a CPU accessing its **own local memory** is fast; accessing memory attached to a **different socket** is slower, because the request has to cross that interconnect.

### Why it matters

- A process running on CPU socket 0 but whose memory happens to be allocated on socket 1's RAM experiences extra latency on every memory access — this is a "remote" access, versus a fast "local" one.
- On a 2-socket server this might mean a difference of roughly 30-50% in memory latency depending on hardware; multiply that across a memory-intensive workload and it's a real, measurable performance hit.
- Matters a lot for databases, HPC workloads, and anything latency-sensitive. Matters less for lightweight/bursty workloads that don't hammer memory bandwidth.

### NUMA nodes

Each **NUMA node** = one CPU socket + its locally-attached memory + often specific PCIe/NIC lanes too. A 2-socket server typically has 2 NUMA nodes; some high-end chips even split a single socket into multiple NUMA domains internally (e.g., AMD EPYC's NPS settings).

### Inspecting NUMA topology

```bash
# See NUMA topology — nodes, CPUs per node, memory per node, distances
numactl --hardware

# Quick check via lscpu
lscpu | grep -i numa

# Check which NUMA node a running process's memory landed on
cat /proc/<pid>/numa_maps

# Per-node memory usage stats
numastat

# Per-process NUMA memory stats
numastat -p <pid>
```

Example `numactl --hardware` output:

```
available: 2 nodes (0-1)
node 0 cpus: 0 1 2 3 4 5 6 7
node 0 size: 64000 MB
node 1 cpus: 8 9 10 11 12 13 14 15
node 1 size: 64000 MB
node distances:
node   0   1
  0:  10  21
  1:  21  10
```

The `node distances` table is worth understanding — `10` is the baseline (local access cost), `21` means remote access costs roughly 2.1x as much latency. Higher numbers = more expensive to cross.

## 2. Binding a Process to CPUs via NUMA

The core tuning principle: keep a process's **CPU affinity** and its **memory allocation** on the *same* NUMA node. Mismatching them (CPU pinned to node 0, memory allocated on node 1) can be worse than not pinning at all, since you lose the scheduler's ability to self-correct.

### Using `numactl` (recommended — binds CPU and memory together)

```bash
# Bind both CPU execution and memory allocation to NUMA node 0
numactl --cpunodebind=0 --membind=0 <command>

# Shorthand for "run entirely on node 0" (CPU + memory)
numactl -N 0 -m 0 <command>

# Bind to specific CPU cores (not the whole node) plus memory node
numactl --physcpubind=0-3 --membind=0 <command>

# Prefer a node for memory but allow fallback if it fills up
# (softer than --membind, won't fail if node 0 memory is exhausted)
numactl --preferred=0 <command>

# Interleave memory across multiple nodes (useful for some parallel workloads
# that don't have a single "home" node — e.g. some HPC/scientific codes)
numactl --interleave=all <command>
```

### Using `taskset` (CPU pinning only — no memory awareness)

```bash
# Pin a new process to specific CPU cores
taskset -c 0,1,2,3 <command>

# Pin an already-running process (by PID) to specific cores
taskset -pc 0-3 <pid>

# Check current CPU affinity of a running process
taskset -p <pid>
```

`taskset` only controls **which CPUs** a process can run on — it says nothing about memory locality. If you use `taskset` alone on a NUMA system, the process could still end up with memory allocated on a remote node. This is why `numactl` is generally the better tool when NUMA locality actually matters — it lets you control both dimensions together.

### Checking whether pinning actually helped

```bash
# Confirm current CPU affinity
taskset -p <pid>

# Confirm memory node placement for the process
numastat -p <pid>

# Live view of CPU/node utilization while workload runs
numastat -n 1
```

### Applying this to systemd services or containers

```bash
# systemd unit — restrict a service to specific CPUs
# In the [Service] section of a unit file:
# CPUAffinity=0-3

# Docker — pin container to specific CPUs and a NUMA node's memory
docker run --cpuset-cpus="0-3" --cpuset-mems="0" <image>

# Kubernetes — enable the CPU Manager static policy (kubelet config)
# so Guaranteed-QoS pods with integer CPU requests get exclusive,
# NUMA-aware core pinning automatically
```

## 3. cgroups (Control Groups)

### What it is

A Linux kernel feature that lets you group processes together and enforce **limits, prioritization, and accounting** on their resource usage — CPU, memory, disk I/O, and network. It's the underlying mechanism that makes containers work (Docker, Kubernetes, and systemd services all use cgroups under the hood).

### What cgroups control, per group of processes

| Controller | What it limits |
|---|---|
| **CPU** | CPU time — relative shares/weight for priority, or a hard quota (e.g., "at most 2 cores") |
| **Memory** | A hard memory limit; exceeding it triggers the OOM killer **scoped to that group**, not the whole host |
| **Block I/O (`io`)** | Disk read/write bandwidth or IOPS caps per group |
| **PIDs** | Caps the number of processes/threads a group can spawn — prevents fork bombs |
| **cpuset** | Restricts which specific CPUs and NUMA memory nodes a group's processes can use — this is the controller that ties cgroups directly to NUMA pinning |
| **Network** | Traffic shaping/prioritization, less commonly configured directly |

### cgroups v1 vs v2

| | v1 | v2 |
|---|---|---|
| Hierarchy | Separate hierarchy per resource type (multiple mount points) | Single unified hierarchy |
| Mount point | Multiple, e.g. `/sys/fs/cgroup/memory`, `/sys/fs/cgroup/cpu` | One: `/sys/fs/cgroup/` |
| Adoption | Older, still present on some systems | Default on modern distros (Ubuntu 21.10+, RHEL 9+) |
| Complexity | Messier — resource controllers could disagree on process grouping | Cleaner — one consistent view of the whole tree |

### Practical commands

```bash
# View the cgroup(s) a process belongs to
cat /proc/<pid>/cgroup

# cgroups v2 — inspect memory limit and current usage
cat /sys/fs/cgroup/<group>/memory.max
cat /sys/fs/cgroup/<group>/memory.current

# cgroups v2 — CPU limit (quota/period, "max" = unlimited)
cat /sys/fs/cgroup/<group>/cpu.max

# cgroups v2 — restrict which CPUs/NUMA memory nodes a group can use
cat /sys/fs/cgroup/<group>/cpuset.cpus
cat /sys/fs/cgroup/<group>/cpuset.mems

# systemd services are cgroup-scoped by default
systemctl status <service>

# Live resource usage per cgroup, similar to top
systemd-cgtop

# Full cgroup hierarchy tree
systemd-cgls
```

### Why this matters for troubleshooting

A common real-world trap: a critical service gets OOM-killed even though the **host** has plenty of free memory. If the workload is containerized, the container's own memory cgroup limit — not host memory — is often what got hit. Diagnosing this correctly means checking the cgroup's `memory.max` / `memory.current` (or the container runtime's configured limit) rather than assuming a host-level memory shortage from `free -h` alone.

### Docker/Kubernetes connection

Every container is backed by a cgroup. Setting `--memory=512m` on `docker run`, or `resources.limits.memory` in a Kubernetes pod spec, configures a cgroup under the hood. Recognizing this distinction — cgroup-scoped resource event vs host-level event — is what separates understanding the underlying mechanism from just knowing the higher-level abstraction (Docker/K8s) sitting on top of it.

## 4. How NUMA and cgroups Connect

In a well-tuned bare-metal/HPC environment, both are often combined: use the **`cpuset` cgroup controller** to pin a container or workload to specific CPUs, and ensure those CPUs and the memory cgroup's allowed NUMA node are aligned to the **same** NUMA node — giving the workload both resource isolation (cgroups) and memory-locality performance (NUMA) at once.

```bash
# Example: restrict a cgroup to NUMA node 0's CPUs and memory together
echo 0-7 > /sys/fs/cgroup/<group>/cpuset.cpus
echo 0 > /sys/fs/cgroup/<group>/cpuset.mems
```

In Kubernetes, this is the mechanism behind the **CPU Manager static policy** and **Topology Manager** — for Guaranteed-QoS pods with integer CPU requests, the kubelet configures the pod's cgroup `cpuset` to pin it to specific, NUMA-aligned cores automatically, rather than leaving it to the default shared CFS scheduling.

## Quick Interview Talking Points

- **NUMA in one line:** "Memory access time depends on which CPU socket you're on relative to where the memory physically lives — local access is fast, remote access crosses an interconnect and is slower."
- **cgroups in one line:** "The kernel mechanism for grouping processes and enforcing/accounting resource limits — CPU, memory, I/O, PIDs — and it's what containers are built on top of."
- **The connective insight to volunteer:** OOM kills and "why is my container slow" issues are often cgroup-scoped, not host-scoped — and pinning workloads without keeping CPU and memory locality aligned (NUMA) can hurt more than help. Mentioning `cpuset` as the controller that ties cgroups and NUMA together shows depth beyond the individual definitions.
