# Ansible — Complete Reference Layout

A structured walkthrough of Ansible from fundamentals to enterprise practices, with a simple plain-language explanation of every term.

---

## 1. Fundamentals & Architecture

### Core Concepts

- **Control node** — the machine you run Ansible *from*. This is where playbooks live and commands are executed from. Ansible itself only needs to be installed here.
- **Managed nodes** — the servers being configured. They don't need Ansible installed at all.
- **Agentless architecture** — unlike Puppet/Chef (which need an agent daemon running on every managed node), Ansible pushes instructions out over SSH on demand and leaves nothing running afterward. Nothing to install, patch, or maintain on the target fleet.
- **SSH execution** — Ansible's default transport is SSH (WinRM for Windows targets). It logs in, copies a small Python script over, runs it, and cleans up.
- **Python requirement** — managed nodes need Python installed (most modules are Python under the hood), though newer Ansible versions can auto-detect the interpreter or use raw SSH/shell for very minimal targets.

### Inventory Management

The **inventory** is the list of hosts Ansible manages, plus how they're grouped and what variables apply to them.

- **Static inventory (INI format)** — the classic simple format:
```ini
[webservers]
web1.example.com
web2.example.com

[dbservers]
db1.example.com ansible_user=admin
```

- **Static inventory (YAML format)** — same idea, structured as YAML:
```yaml
webservers:
  hosts:
    web1.example.com:
    web2.example.com:
dbservers:
  hosts:
    db1.example.com:
      ansible_user: admin
```

- **Dynamic inventory** — instead of a static file, a script or plugin queries a live source (AWS, GCP, VMware, MAAS, etc.) and generates the inventory on the fly. Essential when your fleet changes constantly (autoscaling, cloud environments) rather than being a fixed list.

- **Host/group variables** — variables scoped to a specific host (`host_vars/web1.example.com.yml`) or a whole group (`group_vars/webservers.yml`), keeping variable data separate from the inventory listing itself.

- **Inventory precedence** — when the same variable is defined in multiple places (host var, group var, `all` group), Ansible has defined rules for which wins — more specific scope generally beats more general scope.

- **Patterns** — how you target hosts when running a playbook or ad-hoc command:
```bash
ansible webservers -m ping          # target a group
ansible 'web*' -m ping              # wildcard pattern
ansible 'webservers:!web2' -m ping  # exclude a host
ansible 'webservers:dbservers' -m ping  # union of two groups
```

### Ansible Configuration

`ansible.cfg` controls Ansible's own behavior (not the managed nodes' behavior).

- **Precedence order** — Ansible looks for `ansible.cfg` in this order, first match wins:
  1. `ANSIBLE_CONFIG` environment variable (explicit override)
  2. `./ansible.cfg` (current directory)
  3. `~/.ansible.cfg` (user's home directory)
  4. `/etc/ansible/ansible.cfg` (system-wide default)

- **Key parameters:**

| Parameter | Purpose |
|---|---|
| `forks` | How many hosts to run tasks against in parallel (default 5 — often bumped up for larger fleets) |
| `remote_user` | Default SSH user to connect as |
| `private_key_file` | Path to the SSH key used for authentication |
| `host_key_checking` | Whether to verify SSH host keys (often disabled in dynamic/ephemeral environments, but a real security tradeoff to be aware of) |

### Ad-Hoc Commands

One-off commands run directly from the CLI without writing a playbook — useful for quick checks or simple, non-repeated tasks.

```bash
ansible all -m ping                                    # connectivity check
ansible webservers -m command -a "uptime"               # run a command
ansible webservers -m shell -a "df -h | grep sda"        # shell (supports pipes/redirects, command doesn't)
ansible webservers -m copy -a "src=file.txt dest=/tmp/"  # copy a file
ansible webservers -m service -a "name=nginx state=restarted"
ansible webservers -m apt -a "name=curl state=present" --become
```

**`command` vs `shell`:** `command` runs a binary directly and does *not* go through a shell — no pipes, redirects, or environment variable expansion. `shell` runs through `/bin/sh`, so pipes/redirects work, but it's slightly less safe/predictable and generally used only when you actually need shell features.

## 2. Playbooks & Task Execution

### Playbook Structure

A **playbook** is a YAML file describing one or more **plays** — each play maps a group of hosts to a set of tasks to run against them.

```yaml
- name: Configure web servers
  hosts: webservers
  become: true                 # escalate privileges (like sudo)
  become_user: root
  become_method: sudo
  tasks:
    - name: Install nginx
      apt:
        name: nginx
        state: present
```

- **become** — escalate privileges for a task/play, equivalent to running as `sudo`.
- **become_user** — which user to escalate to (defaults to root).
- **become_method** — the mechanism used (`sudo` is default; `su`, `pbrun`, others exist for different environments).

### Task Control & Execution

- **Conditionals (`when`)** — only run a task if a condition is true:
```yaml
- name: Restart service on Ubuntu only
  service:
    name: nginx
    state: restarted
  when: ansible_facts['os_family'] == "Debian"
```

- **`failed_when`** — override Ansible's default success/failure logic for a task (e.g., treat a normally "successful" exit code as a failure based on output content).
- **`changed_when`** — override whether a task reports as "changed" — useful for command/shell tasks where Ansible can't automatically tell if something actually changed.

- **Loops:**
```yaml
- name: Install multiple packages
  apt:
    name: "{{ item }}"
    state: present
  loop:
    - curl
    - git
    - vim
```
`loop` is the modern, preferred syntax. `with_items` is the older equivalent (still works, mostly seen in legacy playbooks). `with_dict` loops over a dictionary rather than a list. `until` retries a task repeatedly until a condition is met (paired with `retries` and `delay`) — useful for waiting on a service to become ready.

- **Asynchronous execution (`async`/`poll`)** — run a long task in the background rather than blocking:
```yaml
- name: Long-running task
  command: /opt/long_script.sh
  async: 3600      # max time allowed to run, in seconds
  poll: 10         # check back every 10 seconds (poll: 0 = fire-and-forget, don't wait at all)
```

- **Error handling (`block`/`rescue`/`always`)** — similar to try/catch/finally in programming:
```yaml
- block:
    - name: Risky task
      command: /opt/might_fail.sh
  rescue:
    - name: Recovery step
      debug:
        msg: "The risky task failed, running recovery"
  always:
    - name: Always runs regardless of outcome
      debug:
        msg: "Cleanup step"
```
- **`ignore_errors: true`** — simpler than block/rescue; just tells Ansible to continue past a failed task without stopping the whole play. Less structured than block/rescue since there's no dedicated recovery logic.

- **Tags** — label tasks so you can selectively run or skip them:
```yaml
- name: Install package
  apt:
    name: nginx
  tags:
    - install
```
```bash
ansible-playbook site.yml --tags install
ansible-playbook site.yml --skip-tags install
```

### Handlers

Special tasks that only run when **notified** by another task, and only if that task reported a "changed" state — commonly used for "restart the service only if its config actually changed" logic.

```yaml
tasks:
  - name: Update config file
    template:
      src: nginx.conf.j2
      dest: /etc/nginx/nginx.conf
    notify: Restart nginx

handlers:
  - name: Restart nginx
    service:
      name: nginx
      state: restarted
```

- **`listen`** — lets multiple tasks trigger the same handler via a shared topic name, useful when several different tasks should all be able to trigger, say, "restart nginx" without each needing to know the handler's exact name.

## 3. Variables, Templates & Vault

### Variable Scopes & Precedence

Ansible has a well-defined but famously long precedence order (roughly 20+ levels) for what happens when the same variable is set in multiple places. From lowest to highest priority, broadly:

1. Role defaults (`defaults/main.yml`) — lowest priority, easily overridden
2. Inventory group/host vars
3. Playbook group/host vars
4. Play vars
5. Task vars
6. Role vars (`vars/main.yml`) — higher priority than role defaults
7. Extra vars (`-e` on the command line) — **highest priority, always wins**

**Practical rule of thumb:** put a sensible default in role `defaults/`, let inventory/group_vars override it for environment-specific values, and reach for `-e` only for one-off overrides at runtime.

### Ansible Facts

**Facts** are auto-discovered information about a managed host — OS version, IP addresses, CPU count, memory, disk layout — gathered automatically before tasks run.

```bash
ansible webservers -m setup     # manually trigger fact gathering and see all facts
```

```yaml
- name: Show OS family
  debug:
    msg: "{{ ansible_facts['os_family'] }}"
```

- **Custom facts** — you can define your own facts on a managed node by dropping `.fact` files (INI, JSON, or executable scripts) into `/etc/ansible/facts.d/` on that host; Ansible picks them up automatically during fact gathering as `ansible_local`.
- **Disabling fact gathering** — if you don't need facts (or want faster playbook runs), set `gather_facts: false` in a play — meaningfully speeds up large runs where facts aren't actually used.

### Jinja2 Templating

Ansible uses **Jinja2** (a Python templating engine) for variable substitution and logic inside both playbooks and template files.

```jinja
Server: {{ inventory_hostname }}
{% if ansible_facts['os_family'] == "Debian" %}
This is a Debian-based system.
{% endif %}

{% for user in users %}
User: {{ user.name }}
{% endfor }}
```

- **Filters** — transform a value inline: `{{ some_list | map(attribute='name') | list }}`, `{{ my_var | default('fallback_value') }}`, `{{ users | selectattr('active') | list }}`. Custom filters can also be written in Python if the built-in ones don't cover what you need.
- **The `template` module** — renders a `.j2` Jinja2 file and copies the result to the managed node, substituting all variables/logic:
```yaml
- name: Deploy config from template
  template:
    src: app.conf.j2
    dest: /etc/app/app.conf
```

### Ansible Vault

Encrypts sensitive data (passwords, API keys, certificates) so secrets can be safely committed to version control alongside the rest of your playbooks.

```bash
ansible-vault create secrets.yml        # create a new encrypted file
ansible-vault edit secrets.yml          # edit an existing encrypted file
ansible-vault encrypt existing_file.yml # encrypt a file that already exists
ansible-vault decrypt secrets.yml       # decrypt permanently
ansible-vault view secrets.yml          # view without decrypting to disk

# Run a playbook that references vault-encrypted vars
ansible-playbook site.yml --ask-vault-pass
ansible-playbook site.yml --vault-password-file ~/.vault_pass.txt
```

- **Multiple vault IDs** — lets you use different vault passwords for different environments/purposes (e.g., separate passwords for `dev` vs `prod` secrets) rather than one password for everything:
```bash
ansible-vault encrypt --vault-id prod@prompt secrets_prod.yml
ansible-playbook site.yml --vault-id prod@~/.vault_pass_prod.txt
```

## 4. Modularization & Reusability

### Includes vs. Imports

Both let you break playbooks into reusable pieces, but they behave differently:

| | Dynamic (`include_*`) | Static (`import_*`) |
|---|---|---|
| When processed | At runtime, as the play executes | At parse time, before the play starts |
| Can use variables in the path | Yes (e.g., `include_tasks: "{{ env }}.yml"`) | No — path must be known upfront |
| Works with `when` conditionally per-task | Yes | No — applies the condition to the whole imported block at once, not tested per-task inside |
| Tags/loops behavior | Evaluated at runtime | Evaluated at parse time — slightly more predictable for `--list-tasks` |

```yaml
- include_tasks: setup_{{ ansible_facts['os_family'] }}.yml   # dynamic — path can be variable
- import_tasks: common_tasks.yml                               # static — fixed path
- include_role:
    name: webserver
- import_role:
    name: webserver
```

**Rule of thumb:** use `import_*` for simple, always-the-same structure; use `include_*` when you need runtime flexibility (variable paths, conditional inclusion based on facts discovered during the run).

### Ansible Roles

A **role** is a standardized directory structure that packages up tasks, variables, templates, handlers, and files into a reusable, shareable unit.

```
roles/
  webserver/
    defaults/main.yml    # lowest-priority default variables
    vars/main.yml        # higher-priority variables
    tasks/main.yml        # the actual task list
    handlers/main.yml     # handlers for this role
    templates/            # Jinja2 templates used by this role
    files/                 # static files to copy as-is
    meta/main.yml          # role metadata, including dependencies on other roles
```

- **`defaults/` vs `vars/`** — both hold variables, but `defaults/` is intentionally low-precedence (meant to be easily overridden by the user of the role), while `vars/` is higher-precedence (meant to be more fixed/internal to the role's own logic).
- **`meta/main.yml`** — declares role dependencies (other roles that must run first), author info, supported platforms, and Galaxy metadata if publishing.

```yaml
- hosts: webservers
  roles:
    - webserver
    - { role: firewall, firewall_port: 443 }   # pass a variable into the role
```

### Ansible Collections

A **collection** is a distributable package that bundles roles, modules, plugins, and playbooks together — the modern packaging/distribution format for Ansible content, sitting one level above roles.

- **Namespace structure** — collections are named `namespace.collection_name` (e.g., `community.general`, `ansible.builtin`, `amazon.aws`). The namespace is usually the publisher (a community, a vendor, or your own organization).
- **`galaxy.yml`** — the metadata file at the root of a collection you're building yourself, describing its name, version, dependencies, and authors (conceptually similar to a Python package's `setup.py`/`pyproject.toml`).
- **`requirements.yml`** — a file listing collections (and roles) your project depends on, so they can be installed in one command rather than manually:
```yaml
collections:
  - name: community.general
    version: ">=5.0.0"
  - name: amazon.aws
roles:
  - name: geerlingguy.docker
```
```bash
ansible-galaxy collection install -r requirements.yml
ansible-galaxy install -r requirements.yml   # roles
```

- **Using collection modules:**
```yaml
- name: Use a module from a collection explicitly
  community.general.docker_container:
    name: myapp
    image: myapp:latest

# ansible.builtin is the collection containing all the "core" modules
# (copy, file, template, etc.) — usually you don't need to prefix these
```

**Ansible Galaxy** itself is the public hub (like PyPI or Docker Hub, but for Ansible content) where roles and collections are published and discovered — `ansible-galaxy` is also the CLI tool used to install content from it, whether that hub is the public one or a private/internal one (e.g., Automation Hub in Ansible Automation Platform).

## 5. Core Modules & Integrations

### System & Files

| Module | Purpose |
|---|---|
| `file` | Manage file/directory properties — ownership, permissions, symlinks, existence |
| `copy` | Copy a static file from control node to managed node |
| `template` | Copy a Jinja2 template, rendering variables first |
| `lineinfile` | Ensure a specific line exists (or doesn't) in a file — good for small, targeted edits |
| `blockinfile` | Insert/update/remove a marked block of multiple lines in a file |
| `archive` | Create a compressed archive (tar/zip) |
| `unarchive` | Extract an archive, optionally copying it from the control node first |

### User & Package Management

| Module | Purpose |
|---|---|
| `user` | Create/modify/remove user accounts |
| `group` | Create/modify/remove groups |
| `apt` | Debian/Ubuntu package management |
| `yum`/`dnf` | RHEL/CentOS/Fedora package management |
| `package` | Generic, distro-agnostic package module — picks the right backend automatically (good for cross-distro playbooks) |
| `pip` | Install Python packages |

### Services & Process Control

| Module | Purpose |
|---|---|
| `service` | Generic service control (start/stop/restart/enable) — works across init systems |
| `systemd` | systemd-specific control, exposes more systemd-specific options than the generic `service` module |
| `cron` | Manage cron jobs |
| `reboot` | Reboot a managed node and wait for it to come back before continuing the playbook |

### Network & Security

| Module | Purpose |
|---|---|
| `firewalld` | Manage firewalld rules (RHEL-family) |
| `ufw` | Manage ufw rules (Ubuntu/Debian) |
| `iptables` | Lower-level direct iptables rule management |
| `uri` | Make HTTP requests — API calls, health checks, webhooks |
| `get_url` | Download a file from a URL to the managed node |
| SSH key management | `authorized_key` module manages a user's `authorized_keys` entries |

### Cloud & Containers

| Collection | Purpose |
|---|---|
| `amazon.aws` | AWS resource management (EC2, S3, IAM, etc.) |
| Azure collection (`azure.azcollection`) | Azure resource management |
| `community.docker` | Manage Docker containers, images, networks, compose stacks |
| `kubernetes.core` | Manage Kubernetes resources declaratively from Ansible |

## 6. Advanced Operations & Enterprise Practices

### Performance Tuning

- **`forks`** — the single biggest lever for speed; controls how many hosts Ansible works on simultaneously. Default is 5, which is very conservative for a large fleet — often raised to 20-50+ depending on control node resources.
- **SSH pipelining** — reduces the number of SSH operations per task by piping module code directly over an existing connection instead of writing it to a temp file first. Enabled via `pipelining = True` in `ansible.cfg`; can meaningfully speed up execution, though it requires `requiretty` to be disabled in the target's sudoers config.
- **Mitogen** — a third-party plugin that replaces Ansible's default connection/execution strategy with a more efficient persistent-process model, often cited as giving large speedups (sometimes several times faster) on bigger playbook runs, at the cost of being an extra dependency to maintain.
- **Async/background execution strategies** — covered above (`async`/`poll`) — also relevant here because running truly independent long tasks in the background rather than serially can meaningfully cut overall playbook runtime.

### Developing Custom Extensions

- **Custom modules** — when a built-in or collection module doesn't cover what you need, you can write your own in Python following Ansible's module contract (accepts JSON input, returns JSON output with `changed`/`failed` status).
- **Custom plugins** — Ansible has several plugin types beyond modules:
  - **Lookup plugins** — pull data from an external source into a variable (e.g., reading a file, querying an API) at template-rendering time
  - **Filter plugins** — custom Jinja2 filters beyond the built-in ones
  - **Callback plugins** — hook into Ansible's execution lifecycle to customize output/logging (e.g., sending results to Slack, custom log formatting)
  - **Action plugins** — run logic on the control node *before* a module is even dispatched to the managed node — more powerful/flexible than a plain module but more complex to write

### Testing & Linting

- **`ansible-lint`** — static analysis tool that checks playbooks/roles against Ansible best-practice rules (style, deprecated syntax, common mistakes) — similar in spirit to a linter for any programming language.
- **Molecule** — a proper testing framework for roles: spins up test instances (via Docker, Vagrant, or KVM backends), applies the role, verifies the result, and tears the instance down — brings real test-driven development discipline to infrastructure code.
- **`--check` (check mode)** — a dry-run: shows what *would* change without actually making changes. Not every module fully supports check mode, so treat it as a strong signal rather than a 100% guarantee.
- **`--diff`** — shows the actual before/after content difference for file-based changes (templates, copy, lineinfile), very useful combined with `--check` to review exactly what a run would change before committing to it.

### Enterprise Automation Platforms

- **Ansible Automation Platform (AAP)** — Red Hat's commercial, supported platform wrapping Ansible with a web UI, RBAC, scheduling, and enterprise integrations. **AWX** is the open-source upstream project AAP is built from (same relationship as Kubernetes-to-OpenShift, roughly).
- **Execution environments** — containerized, versioned environments bundling a specific Ansible version plus all the collections/dependencies a set of playbooks needs — solves the "works on my machine" dependency drift problem for automation itself.
- **Automation controller** — the component (within AAP/AWX) that manages job scheduling, credentials, inventories, and RBAC through a web UI/API rather than raw CLI usage.
- **Job templates** — a saved, reusable definition of "run this playbook, against this inventory, with these credentials/variables" — lets non-CLI users (or scheduled/triggered automation) run standardized jobs without needing direct shell access.
- **RBAC (Role-Based Access Control)** — controls who can view/run/edit which job templates, inventories, and credentials — critical for enterprise environments where not everyone should have blanket automation access.
- **Workflows** — chain multiple job templates together into a larger orchestrated pipeline (e.g., "provision infra" → "configure OS" → "deploy app" → "run smoke tests"), with branching logic based on success/failure of each step.
- **Webhooks** — let external systems (GitHub, GitLab, monitoring tools) trigger a job template automatically — e.g., a git push automatically kicking off a deployment playbook run.
