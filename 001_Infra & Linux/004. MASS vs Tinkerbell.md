# MAAS vs Tinkerbell — Bare-Metal Provisioning Architecture

Reference notes comparing Canonical's MAAS and CNCF's Tinkerbell — both solve bare-metal provisioning, but with fundamentally different architectural philosophies. Builds on the IPMI/Redfish/PXE fundamentals already covered.

---

## 1. The Shared Problem Both Solve

Bare-metal servers don't provision themselves the way cloud VMs do — there's no hypervisor API to call. Something has to:

1. Discover the hardware (what's plugged in, what MAC addresses exist)
2. Control power state (via IPMI/Redfish)
3. Trigger a PXE boot
4. Serve an OS image and drive an unattended install (kickstart/preseed/cloud-init)
5. Track the machine's lifecycle (available → deploying → deployed → ready for use)

MAAS and Tinkerbell both automate this end-to-end, but they come from very different design philosophies — one opinionated and all-in-one, the other composable and workflow-driven.

---

## 2. MAAS (Metal as a Service)

Built by Canonical. The philosophy: give you a **complete, opinionated platform** — a single tool that owns DHCP, PXE, power management, and OS deployment, with a web UI and REST API on top.

### Architecture

- **MAAS Region Controller** — the central brain: web UI, API, database (PostgreSQL), and orchestration logic
- **MAAS Rack Controller** — runs closer to the actual hardware (per rack/network segment), handles DHCP, TFTP, and proxies power control commands to BMCs
- **PostgreSQL database** — stores machine inventory, state, and configuration
- Built-in **DHCP and DNS** management — MAAS wants to *own* these services on the network it manages, not sit alongside an existing DHCP server

### Machine lifecycle (MAAS's core state model)

```
New → Commissioning → Ready → Allocated → Deploying → Deployed
                                                          ↓
                                                      Released (back to Ready)
```

- **Commissioning**: MAAS powers on the machine via IPMI/Redfish, PXE boots it into an ephemeral inventory environment, and runs hardware discovery scripts (CPU, RAM, disks, NICs — all auto-detected and recorded)
- **Ready**: hardware is known and available for use
- **Allocated**: reserved for a specific purpose/user but not yet deployed
- **Deploying → Deployed**: OS image is written and the unattended install completes
- **Released**: torn down and returned to the Ready pool for reuse

### Key characteristics

- Auto-discovers and inventories hardware during commissioning — you don't manually describe each server's specs
- Built-in power driver support for IPMI, Redfish, and most major vendor BMCs (iDRAC, iLO) out of the box
- Ships curated OS images (Ubuntu especially well-supported, given Canonical builds it) via "simplestreams"
- Strong web UI — good for teams that want a GUI-first operational experience, not just API/CLI
- Tends to assume it's the **sole authority** on the network segment it manages (DHCP, in particular) — integrating it into an existing complex network with other DHCP servers requires careful planning (relay/VLAN segmentation)

### Basic CLI usage

```bash
# Log in to MAAS CLI
maas login admin http://<maas-server>:5240/MAAS <api-key>

# List machines and their status
maas admin machines read | jq '.[].hostname, .[].status_name'

# Commission a machine
maas admin machine commission <system_id>

# Deploy an OS to a machine
maas admin machine deploy <system_id> distro_series=jammy

# Release a machine back to the pool
maas admin machine release <system_id>
```

## 3. Tinkerbell

A CNCF project (originated at Equinix Metal). The philosophy: **composable building blocks**, not a monolithic platform. Provisioning is expressed as a **workflow** — an explicit, declarative sequence of actions — rather than a fixed state machine baked into the tool.

### Architecture (component-based, not a single binary)

- **Smee** — DHCP/PXE/iPXE service; hands out network boot info to machines
- **Hegel** — metadata service; serves instance/cloud-init-style metadata to booting machines
- **Tink Server** — the workflow engine; stores and serves **Workflows** and **Templates** (the declarative definitions of what should happen to a machine)
- **Tink Worker / Tink Agent** — runs *on* the machine being provisioned (inside an ephemeral OS environment booted via PXE), executes the steps defined in the workflow, and reports status back to Tink Server
- **Rufio** — handles BMC/power management (IPMI, Redfish) as a Kubernetes custom resource — this is the piece that talks to the hardware's out-of-band interface
- Typically deployed **on Kubernetes** itself (Tinkerbell components run as pods), and is commonly paired with **Cluster API Provider for Tinkerbell (CAPT)** to provision bare-metal nodes as part of declarative, GitOps-style Kubernetes cluster lifecycle management

### The Workflow model

Instead of a fixed lifecycle state machine, Tinkerbell provisioning is expressed as a **DAG of Actions** defined in a Template — each action is typically a container image that does one discrete thing:

```yaml
# Simplified conceptual example of a Tinkerbell Template
version: "0.1"
name: ubuntu-install
tasks:
  - name: provision
    worker: "{{.device_1}}"
    actions:
      - name: stream-image
        image: image2disk:latest
        environment:
          IMG_URL: "http://.../ubuntu.raw.gz"
          DEST_DISK: /dev/sda
      - name: write-netplan
        image: writefile:latest
      - name: kexec
        image: kexec:latest
```

Each action runs as a container inside the ephemeral provisioning environment on the target machine — streaming a disk image, writing config files, then `kexec`-ing into the new OS without even needing a physical reboot.

### Key characteristics

- No built-in opinion about DHCP/network ownership the way MAAS has — components are independently deployable and you can integrate with existing infra (e.g., DHCP relay to Smee rather than Smee being the only DHCP server on the network)
- No built-in web UI by default — it's API/CRD-driven, Kubernetes-native (Rufio power management is literally a Kubernetes Custom Resource)
- Far more flexible for **custom** provisioning steps — since a workflow is just a sequence of container actions, you can insert arbitrary steps (firmware checks, custom partitioning logic, security scanning before handoff) that MAAS doesn't have a native mechanism for
- Steeper setup — you're assembling components rather than installing one product
- Strong fit when bare-metal provisioning needs to be part of a **larger Kubernetes-native, GitOps workflow** (via Cluster API) rather than a standalone operational tool

### Basic usage pattern

```bash
# Tinkerbell resources are typically managed as Kubernetes CRDs
kubectl get hardware
kubectl get templates
kubectl get workflows

# Apply a hardware definition (MAC address, IP, etc. for a machine)
kubectl apply -f hardware.yaml

# Apply a template (the DAG of actions)
kubectl apply -f template.yaml

# Trigger a workflow (ties a piece of hardware to a template)
kubectl apply -f workflow.yaml

# Watch workflow progress
kubectl get workflow <name> -o yaml
```

## 4. Side-by-Side Comparison

| | MAAS | Tinkerbell |
|---|---|---|
| Origin | Canonical | Equinix Metal → CNCF |
| Philosophy | Opinionated, all-in-one platform | Composable building blocks |
| Deployment model | Standalone service (region + rack controllers) | Kubernetes-native (pods, CRDs) |
| DHCP ownership | Wants to own it | Optional/integratable via relay |
| Provisioning model | Fixed lifecycle state machine | Declarative Workflow (DAG of actions) |
| Customization | Limited to what MAAS exposes | Highly flexible — any containerized action |
| UI | Full web UI + API | API/CRD-driven, no built-in UI |
| OS support | Best with Ubuntu (curated images) | OS-agnostic (you define the image/actions) |
| Kubernetes integration | Can provision nodes that later join a cluster | Native pairing with Cluster API (CAPT) for GitOps-style cluster lifecycle |
| Best fit | Teams wanting a turnkey, GUI-friendly platform, especially Ubuntu-centric shops | Teams wanting bare metal provisioning as part of a Kubernetes-native, highly automated/custom pipeline |
| Power management | Built-in drivers for IPMI/Redfish/vendor BMCs | Rufio component, IPMI/Redfish as Kubernetes custom resources |

## Interview Questions & Answers

### 1. What's the fundamental architectural difference between MAAS and Tinkerbell?

MAAS is a monolithic, opinionated platform — it wants to own DHCP, PXE, and power management on the network segment it manages, with a fixed lifecycle state machine (Commissioning → Ready → Deployed) and a full web UI. Tinkerbell is a set of composable, independently deployable components (Smee, Hegel, Tink Server, Rufio) built to run on Kubernetes, where provisioning is expressed as a declarative Workflow — a DAG of discrete containerized actions — rather than a fixed built-in lifecycle. MAAS optimizes for a turnkey experience; Tinkerbell optimizes for flexibility and integration into Kubernetes-native automation.

### 2. How does Tinkerbell's Workflow model differ from MAAS's deployment process, and what does that flexibility actually buy you?

MAAS deployment is largely a black box from the user's perspective — you trigger a deploy and it writes an image and runs cloud-init, with limited hooks for custom steps outside what MAAS exposes. Tinkerbell workflows are an explicit DAG of actions, each one a container image doing one discrete job — streaming a disk image, writing a netplan config, running a security scan, `kexec`-ing into the new OS. That buys you the ability to insert arbitrary custom steps anywhere in the pipeline — for example, running a hardware validation check before imaging, or injecting a company-specific configuration step — without fighting the tool's built-in assumptions about what provisioning should look like.

### 3. Why would a team choose Tinkerbell over MAAS if they're already running Kubernetes for everything else?

Tinkerbell is Kubernetes-native by design — its components run as pods, and its resources (Hardware, Templates, Workflows, Rufio's BMC objects) are Kubernetes CRDs, so bare-metal provisioning fits directly into the same `kubectl`/GitOps tooling and mental model already used for everything else. Paired with Cluster API Provider for Tinkerbell, you can manage bare-metal Kubernetes node lifecycle declaratively — the same way you'd manage cloud nodes with a cloud provider's Cluster API implementation — which is a much more consistent operational model than running MAAS as a separate, differently-shaped tool alongside Kubernetes.

### 4. What's a practical challenge in integrating either tool into an existing data center network?

For MAAS, the main challenge is DHCP ownership — MAAS wants to be the DHCP authority on the network segment it manages, so integrating it into a network that already has DHCP infrastructure requires careful VLAN segmentation or relay configuration to avoid conflicts, similar to the general PXE/DHCP conflict issue where two DHCP servers can answer the same request. For Tinkerbell, since it's more composable, the more common challenge is operational complexity — you're standing up and maintaining multiple independent components (Smee, Hegel, Tink Server, Rufio) rather than installing one product, which requires more Kubernetes operational maturity on the team's part.

### 5. How does power management (IPMI/Redfish) fit into each tool's architecture?

MAAS has built-in power driver support for IPMI, Redfish, and most major vendor BMCs baked directly into the rack controller — configuring a machine's power type is part of registering it with MAAS, and MAAS handles the power on/off/PXE-boot-trigger sequence internally as part of its commissioning and deployment lifecycle. Tinkerbell handles this through **Rufio**, a dedicated component that models BMC connections and power actions as Kubernetes Custom Resources — so power state and boot control become just another Kubernetes object you can `kubectl get`/`apply` against, consistent with how the rest of Tinkerbell exposes its state.

### 6. If you were evaluating these two tools for a new HPC bare-metal environment, what would you actually ask the team before recommending one?

I'd ask about existing tooling investment — if the team already runs Kubernetes-native GitOps workflows for everything else, Tinkerbell's consistency with that model is a strong pull, especially if Cluster API is already in use for cluster lifecycle. I'd ask how much customization the provisioning pipeline actually needs — if it's largely standard OS deployment with maybe a config management handoff at the end, MAAS's opinionated, turnkey approach is faster to stand up and lower-maintenance. I'd also ask about the OS mix — MAAS's curated image support is strongest with Ubuntu, so a heavily Ubuntu-centric shop gets more out-of-the-box value there, whereas Tinkerbell being OS-agnostic matters more in a mixed-OS or highly custom-image environment, which is common in HPC where specific driver/kernel versions for GPU or InfiniBand hardware often require custom images anyway.

## Where This Connects to Everything Else Covered

- Both tools sit on top of the **PXE fundamentals** already covered (DHCP → TFTP → bootloader → kernel/initrd → unattended install) — they're orchestration layers automating that flow at fleet scale rather than replacing the underlying mechanism.
- Both rely on **IPMI/Redfish** for power control and boot-order manipulation — MAAS bakes this in natively, Tinkerbell exposes it via Rufio as a Kubernetes-native abstraction.
- The **MAAS vs Tinkerbell** choice mirrors a broader theme worth being able to articulate in an interview: opinionated/turnkey platforms trade flexibility for lower operational overhead, while composable/Kubernetes-native tooling trades initial setup complexity for long-term consistency and extensibility — the same tradeoff shows up comparing, say, a monolithic CI system versus a plugin-based one, and being able to frame it that way signals systems thinking rather than just tool trivia.
