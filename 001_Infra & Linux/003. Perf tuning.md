# Linux Performance Tuning & Disk I/O — Interview Reference

Covers CPU/scheduling, memory, disk I/O, filesystem, and kernel tuning fundamentals, with interview Q&A and scenario-based troubleshooting for an SRE/infrastructure role.

---

## 1. CPU & Scheduling

### Key concepts
- **Load average** vs **CPU utilization** are not the same thing — load average includes processes waiting on I/O (uninterruptible sleep, `D` state), not just CPU-bound ones. High load with low CPU usage almost always points at I/O wait, not compute.
- **NUMA (Non-Uniform Memory Access)**: on multi-socket servers, memory local to a CPU socket is faster than remote memory. Processes/threads pinned to the "wrong" NUMA node take a latency hit — matters a lot for HPC/DB workloads.
- **CPU affinity/pinning**: binding a process to specific cores avoids cache thrashing from the scheduler migrating it, and avoids NUMA cross-talk.
- **C-states / P-states**: CPU power-saving states. Deep C-states save power but add latency waking up — for low-latency workloads (trading systems, HPC), these are often disabled in BIOS/firmware.

### Commands
```bash
# Load average, per-core usage
uptime
mpstat -P ALL 1

# Process states — look for D (uninterruptible sleep) as I/O wait signal
ps -eo pid,stat,comm | grep " D"

# NUMA topology
numactl --hardware
lscpu | grep -i numa

# Pin a process to specific cores
taskset -c 0,1 <command>
numactl --cpunodebind=0 --membind=0 <command>

# Adjust scheduling priority
nice -n 10 <command>          # lower priority
ionice -c2 -n7 <command>      # I/O priority (best-effort, low)

# Live per-process CPU/IO breakdown
top
htop
pidstat -d 1     # per-process disk I/O
```

## 2. Memory

### Key concepts
- **`vm.swappiness`**: 0-100, controls how aggressively the kernel swaps. Default 60 is fine for desktops; database/latency-sensitive servers often set it to 1-10 to avoid swapping hot pages.
- **Hugepages**: larger memory page sizes (2MB/1GB vs default 4KB) reduce TLB misses — important for databases and HPC workloads with large memory footprints.
- **OOM killer**: when the system runs out of memory, the kernel picks a process to kill based on an `oom_score`. You can protect critical processes with `oom_score_adj`.
- **Page cache**: Linux uses "free" RAM aggressively for disk cache — `free -h` showing low "free" but high "available" is normal, not a problem.

### Commands
```bash
# Memory overview — check "available", not just "free"
free -h

# Detailed memory breakdown
cat /proc/meminfo

# Current swappiness / set it
cat /proc/sys/vm/swappiness
sysctl vm.swappiness=10

# Hugepages status
cat /proc/meminfo | grep -i huge
sysctl vm.nr_hugepages=1024

# Protect a process from OOM killer
echo -1000 > /proc/<pid>/oom_score_adj

# Check what OOM killer has done
dmesg | grep -i "out of memory"
journalctl -k | grep -i oom

# Per-process memory usage
ps aux --sort=-%mem | head
smem -r   # if installed, more accurate (accounts for shared memory)
```

## 3. Disk I/O

### Key concepts
- **I/O scheduler**: controls how the kernel orders/merges disk requests.
  - `mq-deadline` — good general-purpose default for SSD/NVMe
  - `none` (noop) — best for NVMe where the device itself handles ordering; scheduler overhead just adds latency
  - `bfq` — better fairness across multiple processes, more overhead, more suited to desktop/mixed workloads than high-throughput servers
- **I/O wait (`%iowait`)**: time CPU spends idle waiting on disk. High iowait = disk is the bottleneck, not CPU.
- **IOPS vs throughput**: small random I/O is IOPS-bound (databases), large sequential I/O is throughput-bound (backups, video). Diagnosing which one you have changes the fix entirely.
- **RAID**: RAID 0 (striping, no redundancy, max performance), RAID 1 (mirroring), RAID 5/6 (parity-based, write penalty), RAID 10 (striped mirrors — best balance of performance + redundancy for databases).

### Commands
```bash
# Current I/O scheduler for a device
cat /sys/block/sda/queue/scheduler
echo mq-deadline > /sys/block/sda/queue/scheduler

# Real-time I/O stats — watch %util and await closely
iostat -xz 1

# Per-process I/O usage
iotop
pidstat -d 1

# Block-level trace for deep I/O debugging
blktrace -d /dev/sda -o - | blkparse -i -

# Disk latency/throughput benchmark
fio --name=randread --ioengine=libaio --rw=randread --bs=4k \
    --size=1G --numjobs=4 --runtime=60 --group_reporting

# Check disk health (SMART)
smartctl -a /dev/sda

# Software RAID status
cat /proc/mdstat
mdadm --detail /dev/md0

# Filesystem-level check
df -h
du -sh /path/* | sort -rh | head
```

**Reading `iostat -xz` output — the fields that matter:**
- `%util` — how busy the device is (close to 100% = saturated)
- `await` — average time (ms) for I/O requests, including queue wait — the real "is this slow" number
- `svctm` — service time (deprecated in newer iostat, but conceptually the actual device response time vs queueing)
- `r/s`, `w/s` — reads/writes per second (IOPS)
- `rkB/s`, `wkB/s` — throughput

## 4. Filesystem Choice

| Filesystem | Best for | Notes |
|---|---|---|
| **ext4** | General purpose, stability | Mature, predictable, slightly less scalable for very large files/volumes |
| **XFS** | High-throughput, large files | Better parallel I/O scaling, common default on RHEL for data-heavy workloads |
| **Btrfs** | Snapshots, checksumming | CoW filesystem, built-in snapshots/compression, less common in performance-critical prod |
| **ZFS** | Data integrity, storage pools | Strong checksumming/self-healing, higher memory overhead (ARC cache), common in storage-heavy setups |

For an HPC/high-throughput bare-metal context, XFS is usually the safer default answer unless there's a specific reason (snapshots, dedup) to reach for ZFS/Btrfs.

## 5. Kernel Tuning (`sysctl`)

```bash
# View current value
sysctl net.core.somaxconn

# Set temporarily (until reboot)
sysctl -w net.core.somaxconn=4096

# Persist across reboots
echo "net.core.somaxconn = 4096" >> /etc/sysctl.d/99-tuning.conf
sysctl -p /etc/sysctl.d/99-tuning.conf
```

**Common tunables worth knowing by name and purpose:**

| Parameter | Purpose |
|---|---|
| `vm.swappiness` | How aggressively to swap (lower = prefer RAM) |
| `vm.dirty_ratio` / `vm.dirty_background_ratio` | % of memory that can hold "dirty" (unwritten) pages before forced/background flush to disk |
| `net.core.somaxconn` | Max queued connections for a listening socket |
| `net.ipv4.tcp_tw_reuse` | Allow reuse of sockets in TIME_WAIT — helps high-connection-churn servers |
| `fs.file-max` | System-wide max open file descriptors |
| `vm.nr_hugepages` | Number of hugepages reserved |
| `net.core.rmem_max` / `wmem_max` | Max socket buffer sizes — relevant for high-throughput networking |

## Interview Questions & Answers

### 1. Load average is high but CPU utilization looks fine. What's your diagnosis approach?

High load with low CPU usage points to processes waiting on something other than CPU — almost always disk I/O. I'd check `ps -eo pid,stat,comm` for processes in `D` state (uninterruptible sleep, usually waiting on disk), then confirm with `iostat -xz 1` looking at `%util` and `await`. If I/O is saturated, I'd use `iotop` or `pidstat -d` to find which process is generating the I/O, then decide whether it's a legitimate workload spike, a runaway process, or an underlying disk/storage problem (failing disk, undersized IOPS for the workload).

### 2. Explain the difference between `vm.dirty_ratio` and `vm.dirty_background_ratio`.

Both control how much "dirty" (modified but not yet written to disk) memory the kernel allows before acting. `dirty_background_ratio` is the threshold at which the kernel starts flushing dirty pages to disk asynchronously in the background, without blocking applications. `dirty_ratio` is a higher threshold at which the kernel forces synchronous writes, blocking the writing process until enough dirty pages are flushed. Tuning these matters for write-heavy workloads — too high, and you risk a large burst of writes causing a latency spike when the forced flush finally happens; too low, and you lose the benefit of write-back caching.

### 3. When would you choose the `none`/noop I/O scheduler over `mq-deadline` or `bfq`?

`none` is generally best for NVMe SSDs, because the scheduler's job — reordering and merging requests to reduce seek time — is designed around spinning disk physics. NVMe devices have no seek penalty and typically have their own internal queuing/optimization, so an OS-level scheduler just adds CPU overhead and latency without benefit. `mq-deadline` is a reasonable general default when you still want some fairness/ordering guarantees. `bfq` is better when you need fairness across many competing processes (desktop/interactive workloads) but adds more overhead, so it's less common on high-throughput servers.

### 4. What's the difference between IOPS-bound and throughput-bound workloads, and why does the distinction matter?

IOPS-bound workloads (databases, small random reads/writes) are limited by how many individual I/O operations the storage can process per second, regardless of size — latency per operation matters most. Throughput-bound workloads (large sequential I/O like backups, video streaming, big file transfers) are limited by MB/s bandwidth. The distinction matters because the fix is different: an IOPS problem is usually solved with faster media (NVMe over SATA SSD), more parallelism, or RAID levels that don't add write penalty (RAID 10 over RAID 5). A throughput problem is solved with wider stripes, more drives in parallel, or a faster interconnect. Diagnosing which one you have — using `iostat` to check IOPS (`r/s`/`w/s`) vs throughput (`rkB/s`/`wkB/s`) relative to the device's rated specs — is the first step before touching any config.

### 5. How would you tune a server for a latency-sensitive workload (e.g., trading system or real-time processing)?

Disable deep C-states and set the CPU power governor to `performance` (via BIOS/firmware or `cpupower` at the OS level) to avoid wake-latency from power-saving states. Pin critical processes to specific cores with `taskset`/`numactl`, keeping them on the same NUMA node as the memory and NIC they use most, to avoid cross-socket latency. Consider isolating those cores from the general scheduler entirely with `isolcpus` or `cgroups` so the kernel doesn't schedule other work on them. Use hugepages if the workload has a large memory footprint, to reduce TLB miss overhead. On the networking side, this is also where you'd look at IRQ affinity tuning and potentially bypass the kernel network stack (DPDK/RDMA) if truly ultra-low-latency is required.

### 6. Explain what page cache is and why "low free memory" on Linux is often not a problem.

Linux aggressively uses otherwise-idle RAM to cache recently-accessed disk pages, since RAM is much faster than disk and this cache can be reclaimed instantly if an application needs the memory. This means `free -h`'s "free" column often looks alarmingly low while the "available" column (which accounts for reclaimable cache) shows plenty of headroom. The mistake to avoid is treating a full page cache as a memory shortage — it's actually the kernel using memory efficiently. The real signal to watch for a genuine problem is swap usage increasing or the OOM killer firing, not a low raw "free" number.

### 7. What's the difference between RAID 5, RAID 6, and RAID 10, and when would you choose each?

RAID 5 stripes data with a single parity block distributed across disks — good capacity efficiency, but has a write penalty (each write requires reading/recalculating parity) and can't survive a second disk failure during a rebuild. RAID 6 adds a second parity block, tolerating two disk failures, at the cost of more write overhead and capacity. RAID 10 stripes across mirrored pairs — no parity calculation overhead, excellent read/write performance, and can survive multiple failures as long as they're not both disks in the same mirrored pair, but at the cost of losing half your raw capacity. For databases or any write-heavy, latency-sensitive workload, RAID 10 is usually the right answer despite the capacity cost; RAID 5/6 make more sense for capacity-oriented, read-heavy, or backup-tier storage.

### 8. How do hugepages improve performance, and what's the tradeoff?

Standard memory pages are 4KB, and the CPU's Translation Lookaside Buffer (TLB) — a cache that maps virtual to physical addresses — has limited entries. A process with a large memory footprint using 4KB pages generates far more TLB entries than the TLB can hold, causing frequent TLB misses that require a slower page-table walk. Hugepages (2MB or 1GB) drastically reduce the number of pages needed to cover the same memory, reducing TLB pressure and improving performance for memory-intensive workloads like databases or HPC applications. The tradeoff is reduced flexibility — hugepages are typically pre-allocated and reserved, can't be swapped, and if over-provisioned, waste memory that other processes can't use.

### 9. A disk shows high `%util` in `iostat` but the application doesn't seem noticeably slow. Is this a problem?

Not necessarily — `%util` measures how much time the device had at least one I/O request outstanding, which for a single-queue-depth device can hit 100% even at fairly low actual load. The more meaningful number alongside it is `await` (actual latency experienced) — if `await` is low and stable, the application isn't actually suffering even if `%util` looks saturated, especially on devices/controllers that support high queue depths (NVMe can have many requests in flight and still show good latency at high %util). I'd look at `await`, application-level latency metrics, and whether NVMe/SSD queue depth settings match the workload before concluding there's an actual problem.

### 10. What steps would you take to establish a performance baseline before troubleshooting a "server is slow" ticket?

Before touching anything, I'd capture a snapshot across all the major subsystems: `uptime`/`mpstat` for CPU and load, `free -h` for memory, `iostat -xz` for disk, `sar` (if historical data is enabled) to see whether this is a new condition or a gradual trend, and `dmesg`/`journalctl` for any recent kernel-level errors (OOM kills, disk errors, thermal throttling). I'd also check whether "slow" is reported at the OS level or purely at the application level — sometimes the OS is healthy and the bottleneck is in application code, a database query, or an external dependency, which changes the entire direction of the investigation. Having baseline metrics from before the issue started (via Prometheus/Grafana if available) is the fastest way to confirm what actually changed rather than guessing from a single point-in-time snapshot.

## Top 10 Scenario-Based Questions & Approach

### 1. A database server's disk I/O wait suddenly spiked from near-zero to 40% during business hours, and query latency has gotten much worse. Walk me through your investigation.

**Approach:** Confirm the timeline first — check Grafana/Prometheus (or `sar` if historical data is retained locally) to see exactly when it started and whether it correlates with a deploy, a batch job, or a traffic pattern change. Run `iostat -xz 1` to confirm which device is saturated and check `await` to quantify actual latency impact. Use `iotop`/`pidstat -d` to identify the specific process(es) driving the I/O — is it the database itself doing legitimate work, a backup job that started running concurrently, or something unexpected like a runaway log-writing process. If it's the database, check whether this is a genuine workload increase (more queries/larger result sets) versus a query plan regression (a query that used to use an index now doing a full table scan, which massively increases I/O for the same logical request). Only after identifying the actual driver would I consider infra-level fixes like moving to faster storage or spreading I/O load — jumping straight to hardware changes without root-causing the query/workload pattern risks masking a recurring problem.

### 2. A server's memory usage looks nearly full in monitoring, but the on-call engineer says the application isn't reporting any issues. Is there anything to worry about?

**Approach:** First distinguish "used" from "available" memory — Linux's page cache behavior often makes memory look fully consumed when in fact most of it is reclaimable cache. I'd check `free -h`'s "available" column specifically, not just "used," and cross-reference with swap usage (`free -h` swap row, or `vmstat 1` watching the `si`/`so` columns) — if swap is idle and available memory is healthy, there's likely no real problem, just a dashboard/alert threshold that's misconfigured to watch "used" instead of "available." If swap usage is actively climbing or the OOM killer has fired (`dmesg | grep -i oom`), that's a real signal worth escalating regardless of what the application itself is reporting, since OOM kills can silently take down secondary processes without the primary application logging anything unusual.

### 3. You're told a batch of newly provisioned bare-metal servers are performing 20-30% slower than an existing, supposedly identical batch on the same workload. How do you find the difference?

**Approach:** Don't assume software first — since these are freshly provisioned bare metal, I'd check firmware/BIOS settings via Redfish/IPMI across both batches before diving into OS-level tuning, since a default BIOS power profile, disabled Turbo Boost, or different C-state configuration between batches is a very common and easy-to-miss cause. Compare `lscpu`, `dmidecode`, and `ethtool`/NIC firmware versions to rule out a hardware/firmware revision difference. On the OS side, diff `sysctl -a` output and I/O scheduler settings between a working and underperforming host — if these were imaged via PXE/MAAS with a slightly different kickstart profile or a config management run that didn't fully converge, settings can silently drift. Only after ruling out firmware and OS config would I look at application-level differences (different kernel version, different container runtime version, etc.).

### 4. An application team reports "random" latency spikes every few hours with no clear pattern. What's your systematic approach?

**Approach:** "Random" is usually a signal that no one has correlated it against anything yet, so the first step is building a timeline of the spikes against every layer — CPU, memory, disk I/O, network, and any scheduled jobs (cron, log rotation, backups, GC pauses if it's a JVM app) — using whatever time-series data is available in Prometheus. Cron jobs and log rotation are extremely common sources of "every few hours, no obvious pattern" latency because they run on fixed intervals that don't obviously map to business traffic. I'd also check for dirty page flush behavior (`vm.dirty_ratio` triggering a forced synchronous write) if the spikes correlate with sustained write activity, and check whether NUMA cross-node access or CPU throttling (thermal or power-limit related, checkable via BMC sensor data) lines up with the timing. The key discipline here is refusing to accept "random" and instead finding the actual periodic trigger.

### 5. A server is intermittently dropping into very high `%iowait` for a few seconds at a time, but `iostat` averaged over a minute doesn't show anything unusual. How do you catch it?

**Approach:** Averaging over too long an interval smooths out short spikes, so I'd drop `iostat`'s sampling interval down to 1 second (`iostat -xz 1`) and let it run continuously, ideally capturing output to a file so I can correlate exact timestamps against application logs. If the spike is too short-lived even for 1-second sampling to reliably catch, `blktrace`/`blkparse` gives sub-second, request-level detail on exactly what I/O is happening and when. I'd also check whether this correlates with something bursty and predictable, like a log rotation, a cron-triggered sync, or SSD garbage collection/TRIM activity on the underlying device — some SSDs show brief latency spikes during background garbage collection under sustained write load.

### 6. You need to decide between RAID 10 and RAID 6 for a new database server. How do you make that call, and what would you ask the team requesting it?

**Approach:** I'd ask about the actual workload profile — read/write ratio, whether it's latency-sensitive (OLTP-style small transactions) or throughput/capacity-oriented (data warehouse, mostly-read analytics), and what the acceptable usable-capacity-vs-raw-capacity tradeoff is, since RAID 10 costs 50% of raw capacity while RAID 6 is much more capacity-efficient. For a transactional database with meaningful write load, I'd push for RAID 10 given its lack of parity write penalty and better rebuild characteristics (RAID 6 rebuilds are I/O-intensive and slow on large arrays, during which performance degrades and a second concurrent failure is more consequential). If the team's actual need is closer to bulk storage or infrequent-write analytics, I'd point out RAID 6 is probably the more cost-effective right answer and RAID 10 would be over-engineering the storage layer for a workload that doesn't need it.

### 7. A newly deployed server keeps getting its critical service killed by the OOM killer even though total memory usage doesn't look excessive. What would you check?

**Approach:** I'd check the actual OOM kill log details (`dmesg` or `journalctl -k`) for the memory cgroup/limit context — if this is a containerized workload, the container's own memory cgroup limit (not the host's total memory) may be what's being hit, which can happen even when the host has plenty of free RAM. I'd check the container/cgroup's configured memory limit against its actual usage pattern, and check whether the application has a memory leak or a burst pattern (e.g., large batch processing) that occasionally exceeds a limit set based on average rather than peak usage. If it's not containerized, I'd check the process's `oom_score_adj` — if it wasn't protected and a memory-hungry sibling process pushed system memory pressure high, the kernel's OOM killer heuristic may have selected the critical service simply based on its score rather than it being the actual cause of the pressure.

### 8. You're asked to prep a fleet of bare-metal nodes for a latency-sensitive HPC workload before the application team starts testing. What's your pre-flight checklist?

**Approach:** Starting at the firmware layer since these are freshly provisioned bare metal — set BIOS power profile to performance mode, disable deep C-states, and confirm consistent firmware/BIOS versions across the fleet via Redfish, since inconsistent firmware is a common source of "some nodes are slower" complaints discovered too late. At the OS level, set the CPU governor to `performance`, configure `isolcpus`/CPU pinning if the workload benefits from dedicated cores, allocate hugepages if the application needs a large memory footprint, and tune the I/O scheduler appropriately for the underlying storage (NVMe = `none`). On the networking side, if InfiniBand is involved, verify subnet manager health and `ibstat` link status across all nodes before handing off. Finally, I'd run a quick synthetic benchmark (`fio` for disk, a simple CPU/memory stress test) across the whole fleet to confirm consistent baseline performance node-to-node before the application team starts testing — catching an outlier node here is much cheaper than debugging a "some jobs run slower" mystery after testing has started.

### 9. During a postmortem, it turns out a performance issue was caused by a `sysctl` change that was applied months ago and forgotten. How do you prevent this going forward?

**Approach:** This is fundamentally a documentation/change-management gap rather than a technical one, so I'd push for treating `sysctl` and other OS-level tuning as version-controlled configuration rather than ad-hoc manual changes — managed through Ansible/config management with the values committed to a repo, so there's a clear history of what was changed, when, and by whom, tied to a change ticket explaining why. I'd also advocate for a periodic drift-detection check (config management running in a "check/report" mode regularly, even if not auto-applying) to catch manual changes that bypass the documented process. This ties directly into the ITSM/change-management side of the role — the fix isn't just "document better" as a platitude, it's making the automation itself the source of truth so undocumented drift becomes structurally harder to introduce.

### 10. A GPU-based HPC node is reporting good GPU utilization but overall job throughput is worse than expected. What non-GPU factors would you investigate?

**Approach:** High GPU utilization doesn't rule out the GPU being fed inefficiently, so I'd first check whether the bottleneck is actually data movement rather than compute — PCIe bandwidth between CPU and GPU, whether the process feeding the GPU is pinned to the same NUMA node the GPU is attached to (a GPU on a different NUMA node than the process feeding it can add meaningful latency), and disk I/O if the workload is reading large datasets from storage during the job rather than having them pre-staged in memory. If InfiniBand is involved for multi-node jobs, I'd check `ibstat` link speed/state and look for any nodes running at a degraded link rate, since a single degraded node in a multi-node job can bottleneck the whole job's throughput. I'd also check whether hugepages are configured for the host-side data pipeline feeding the GPU, since standard 4KB pages can become a CPU-side bottleneck when staging large volumes of data at high throughput.
