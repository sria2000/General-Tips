# Bare-Metal Out-of-Band Management: IPMI, Redfish, PXE, iDRAC, iLO

Reference notes on out-of-band server management and network boot/provisioning tooling — covers fundamentals, vendor-specific implementations (Dell iDRAC, HPE iLO/Synergy), interview Q&A, and troubleshooting scenarios.

---

## 1. IPMI (Intelligent Platform Management Interface)

Out-of-band management standard for servers. It runs on the **BMC (Baseboard Management Controller)** — a separate chip on the motherboard with its own power feed and network port — so it works even when the host OS is down, hung, or the machine is powered off (as long as it has AC power).

### What it gives you

- Power control (on / off / reset / cycle) regardless of OS state
- Remote console via **Serial-over-LAN (SOL)**
- Sensor data — temperature, fan speed, voltages, power draw
- **SEL (System Event Log)** — hardware error/event history, survives reboots
- Virtual media mounting (attach an ISO/IMG remotely as if it were a physical drive)
- FRU (Field Replaceable Unit) inventory — part numbers, serials

### Key commands (`ipmitool`)

```bash
# Power control
ipmitool -I lanplus -H <bmc-ip> -U admin -P pass power status
ipmitool -I lanplus -H <bmc-ip> -U admin -P pass power on|off|cycle|reset

# Chassis / sensors
ipmitool -I lanplus -H <bmc-ip> -U admin -P pass chassis status
ipmitool -I lanplus -H <bmc-ip> -U admin -P pass sensor list

# Event log
ipmitool -I lanplus -H <bmc-ip> -U admin -P pass sel list
ipmitool -I lanplus -H <bmc-ip> -U admin -P pass sel clear

# BMC network config
ipmitool -I lanplus -H <bmc-ip> -U admin -P pass lan print

# Serial-over-LAN console
ipmitool -I lanplus -H <bmc-ip> -U admin -P pass sol activate

# FRU inventory
ipmitool -I lanplus -H <bmc-ip> -U admin -P pass fru print
```

`-I lanplus` specifies the IPMI v2.0 interface (RMCP+) — almost always what you want over the network rather than the older, weaker `lan` interface.

### Limitations

- Protocol dates to the late 1990s, binary/proprietary rather than a standard data model
- Poor security track record — weak default credentials, known CVEs (e.g. the "Cipher Zero" authentication bypass, and RAKP hash disclosure allowing offline password cracking)
- Limited, vendor-inconsistent data — no standard way to get rich hardware inventory
- This is the main reason **Redfish** was created as a successor

## 2. Redfish

Modern replacement for IPMI, defined by **DMTF**. Same core job — out-of-band server management — but exposed as a RESTful HTTP API with a standardized JSON schema instead of a proprietary binary protocol.

### Key differences from IPMI

| | IPMI | Redfish |
|---|---|---|
| Transport | Binary over UDP (RMCP/RMCP+) | HTTPS / JSON (REST) |
| Data model | Minimal, vendor-inconsistent | Standardized DMTF schema |
| Scriptability | `ipmitool` CLI wrapping binary calls | Native `curl`/Python/Ansible against REST endpoints |
| Security | Weak default auth, known CVEs | TLS + role-based auth |
| Scope | Power, sensors, SEL, SOL | All of the above + storage, NICs, firmware inventory, BIOS settings, update service |

### Example usage

```bash
# Discover the service root
curl -k https://<bmc-ip>/redfish/v1/

# Get system info
curl -k -u admin:pass https://<bmc-ip>/redfish/v1/Systems/1

# Power on a system
curl -k -u admin:pass -X POST \
  https://<bmc-ip>/redfish/v1/Systems/1/Actions/ComputerSystem.Reset \
  -H "Content-Type: application/json" \
  -d '{"ResetType": "On"}'

# Get firmware inventory
curl -k -u admin:pass https://<bmc-ip>/redfish/v1/UpdateService/FirmwareInventory
```

Vendors implement Redfish differently on top of the same base schema — Dell (iDRAC), HPE (iLO), and Lenovo (XCC) all expose Redfish alongside their own proprietary APIs/CLIs, so schema discovery via `/redfish/v1/` and reading the vendor's Redfish resource map matters in practice. Not every vendor exposes every optional Redfish feature.

## 3. PXE (Preboot Execution Environment)

Lets a machine boot over the network instead of from local disk. Used for OS provisioning/imaging at scale — the backbone of most bare-metal automation.

### Boot flow

1. NIC firmware broadcasts a **DHCP** request with the PXE client flag set
2. DHCP server responds with an IP **and** PXE-specific options: option 66 (`next-server` / TFTP server address) and option 67 (`filename` / bootloader name)
3. Machine downloads the bootloader (e.g. `pxelinux.0` for BIOS, `bootx64.efi` for UEFI) via **TFTP**
4. Bootloader fetches a boot menu, then a kernel + initrd
5. **Kickstart** (RHEL/CentOS) or **preseed** (Debian/Ubuntu) file drives the automated, unattended install

### Components

- **DHCP server** — hands out IP + PXE boot options
- **TFTP server** — serves the initial bootloader (TFTP is simple/slow, so it's only used for the small early-stage files)
- **HTTP server** — often serves the larger install tree/packages once past the initial TFTP boot stage, since HTTP is far faster
- **Kickstart/preseed file** — answers all install prompts non-interactively (partitioning, packages, network, post-install scripts)

### Common troubleshooting angle

"PXE boot hangs at TFTP" almost always traces back to one of:
- Firewall blocking UDP port 69 (TFTP)
- Wrong `next-server` value in DHCP
- BIOS vs UEFI boot file mismatch (`.0` legacy vs `.efi`)
- DHCP scope exhausted, or a rogue/second DHCP server on the same VLAN answering first

## 4. Dell iDRAC (Integrated Dell Remote Access Controller)

Dell's BMC implementation — supports both **IPMI** and **Redfish**, plus a proprietary web GUI and `racadm` CLI.

**Licensing tiers matter here** — this is a common interview trap:
- **iDRAC Basic** — minimal remote management
- **iDRAC Express** — adds web GUI, basic remote console
- **iDRAC Enterprise / Datacenter** — full virtual media, full Redfish feature set, licensed features like vFlash

### Key tools

```bash
# racadm (Dell's proprietary CLI, works locally or remotely)
racadm getsysinfo
racadm serveraction powercycle
racadm racreset

# Redfish against iDRAC (same pattern as generic Redfish above)
curl -k -u root:calvin https://<idrac-ip>/redfish/v1/Systems/System.Embedded.1

# Dell's Redfish-based firmware update workflow
curl -k -u root:calvin -X POST \
  https://<idrac-ip>/redfish/v1/UpdateService/Actions/Oem/DellUpdateService.Install \
  -H "Content-Type: application/json" -d '{...}'
```

**Practical notes:**
- Default credentials are often `root` / `calvin` — a real security risk if left unchanged, and a common audit finding
- iDRAC has its own dedicated NIC port (out-of-band), or can share the host's NIC (shared LOM mode) — worth knowing the difference for network design discussions
- Firmware updates can be pushed via iDRAC without touching the host OS at all — useful for patching at scale during maintenance windows

## 5. HPE iLO (Integrated Lights-Out) and HPE Synergy

**iLO** is HPE's BMC, functionally the counterpart to iDRAC — supports Redfish natively (HPE was one of the earliest and most complete Redfish adopters) plus its own `hponcfg`/`ilorest` CLI tooling and a web GUI.

```bash
# ilorest (HPE's Redfish-based CLI tool)
ilorest login <ilo-ip> -u admin -p pass
ilorest list --selector=ComputerSystem.
ilorest reboot

# Direct Redfish call against iLO
curl -k -u admin:pass https://<ilo-ip>/redfish/v1/Systems/1
```

**HPE Synergy** is a step up in scope — a **composable infrastructure** platform, not just a single-server BMC. It manages a whole frame of compute, storage, and fabric modules as a pool of resources that can be composed into logical servers on demand.

- **Composer** — the management appliance/module that orchestrates the frame
- **OneView** — the software layer for defining server profiles, network connectivity, storage volumes, and firmware baselines declaratively
- Synergy applies **server profiles** (a template describing BIOS settings, boot order, network identity, storage config) to physical compute modules — so a physical blade can be reprovisioned as a completely different logical server by reapplying a profile, without manual BIOS/BMC configuration on each box
- Underneath, individual compute modules still expose iLO for direct BMC-level access, but day-to-day operations go through OneView/Composer for consistency across the frame

**Why this matters in an interview:** it shows you understand the difference between managing servers *individually* (IPMI/Redfish/iDRAC/iLO on a box-by-box basis) versus managing them *as a fleet* through a composable/orchestration layer (Synergy/OneView), which is the direction most large-scale infrastructure has moved.

## Interview Questions & Answers

### 1. What's the fundamental architectural difference between IPMI and Redfish, and why did the industry move toward Redfish?

IPMI is a binary protocol running over UDP (RMCP/RMCP+) with a minimal, vendor-inconsistent data model and a weak security history — default credentials, known auth-bypass CVEs, offline hash-cracking exposure. Redfish is a RESTful HTTPS/JSON API built on a standardized DMTF schema, giving a much richer, consistent data model (storage, NICs, firmware, BIOS settings) that's easy to automate with standard HTTP tooling and secured with proper TLS and role-based auth. The industry moved to Redfish because IPMI's security gaps and inconsistent vendor implementations became untenable at data-center scale.

### 2. Walk me through what happens, step by step, from power-on to OS boot, when a server PXE boots.

NIC broadcasts a DHCP request with the PXE flag set → DHCP server replies with an IP plus option 66 (TFTP server) and option 67 (boot filename) → client downloads the bootloader via TFTP → bootloader loads a boot menu and fetches the kernel + initrd (often over HTTP for speed on larger files) → the installer runs, driven by a kickstart (RHEL) or preseed (Debian) file that answers all prompts non-interactively → OS installs and the server reboots into the new install.

### 3. A server won't respond to `ipmitool` commands but the OS (when manually powered on) is fine. How do you troubleshoot the BMC itself?

Check that the BMC's dedicated management NIC has link and a valid IP (`ipmitool lan print` from a working host, or the BMC's own local status via the web GUI/serial if reachable). Confirm you're using the right interface flag (`lanplus` vs `lan`) and correct credentials. Check for BMC hangs — many BMCs support a soft reset independent of the host (`racreset` on iDRAC, or a physical/power-cycle reset). Verify no ACL/firewall is blocking the IPMI port (623/UDP) or the Redfish HTTPS port. If none of that works, a full BMC firmware reset or reflash may be required — this can sometimes be done from the host OS itself since the BMC shares the chassis but is logically separate.

### 4. How would you remotely diagnose a server that's completely unresponsive — no SSH, no ping — using only out-of-band tools?

Connect to the BMC via IPMI or Redfish (independent path, doesn't rely on the host OS or its network). Check `chassis status` / power state first — confirm it's actually powered on. Pull the SEL (`sel list`) for hardware errors — ECC memory faults, CPU thermal events, PSU failures. Check sensor readings for anything out of range. If the OS might be up but networking is broken, activate Serial-over-LAN (`sol activate`) to get a live console without needing the network stack. If it looks like a boot hang, mount a rescue ISO via virtual media and boot into it to investigate further.

### 5. What security concerns exist with IPMI, and how would you mitigate them in a production environment?

Concerns: default/weak credentials shipped by vendors, the Cipher Zero authentication bypass on some older firmware, RAKP-based password hash exposure allowing offline cracking, and the fact that BMC management networks are often left flat/unsegmented. Mitigations: change default credentials immediately, disable Cipher Zero and other legacy ciphers, keep BMC firmware patched, put all BMC management interfaces on a dedicated, firewalled out-of-band management VLAN with no route to production traffic, and prefer Redfish-over-TLS with strong auth where the hardware supports it instead of relying on IPMI alone.

### 6. You need to reimage 200 bare-metal servers overnight with minimal manual intervention. What's your approach using PXE and related tooling?

Use a provisioning framework (Foreman, Cobbler, or MAAS) that ties together DHCP, TFTP/HTTP, and kickstart/preseed generation so each server gets a per-MAC or per-profile config automatically. Drive power state and boot-order changes via IPMI or Redfish scripted in bulk (set next-boot to PXE, then power-cycle) rather than touching each server's BIOS manually. Stage kickstart files with the post-install steps needed (network config, base packages, config management agent bootstrap) so each server comes up ready for Ansible/Puppet/etc. to finish configuration. Monitor via SEL/sensor checks during the run to catch hardware failures rather than assuming every failure is a software issue.

### 7. How do you use Redfish to pull firmware inventory or trigger a firmware update without touching the OS?

Query the `UpdateService/FirmwareInventory` endpoint to list current firmware versions across BIOS, BMC, NICs, storage controllers, etc. To update, POST a firmware image (often referenced by a URI the BMC can pull from, or uploaded directly) to the `UpdateService` action endpoint — vendors add their own OEM actions on top (e.g. Dell's `DellUpdateService.Install`) for more granular control like staging updates for the next reboot. This all happens at the BMC level, independent of whatever OS is or isn't running on the host.

### 8. DHCP is also used for regular server IP assignment — how do you avoid PXE and regular DHCP interfering with each other on the same network?

Ideally, separate PXE boot traffic onto its own VLAN/subnet so there's no ambiguity about which DHCP server should answer. If they must share a network, use **DHCP relay/IP helper** configured to point PXE-specific requests at the provisioning server while normal DHCP is handled elsewhere, or configure a single DHCP server with conditional options based on client vendor class identifier (PXE clients identify themselves distinctly in their DHCP requests, so a properly configured DHCP server can serve different options to PXE vs regular clients from the same server). The key risk to call out is a rogue second DHCP server answering PXE requests with wrong boot file info — switch port DHCP snooping helps prevent that.

### 9. What's the difference between BIOS-mode PXE booting and UEFI PXE booting, and why does it matter for troubleshooting?

BIOS-mode (legacy) PXE uses a 16-bit real-mode boot process and typically loads a file like `pxelinux.0` or `undionly.kpxe`. UEFI PXE boots load an EFI-format bootloader like `bootx64.efi` or `grubx64.efi` and support features like larger disks, Secure Boot, and a more modern boot menu. If the DHCP server is configured to hand out the wrong boot filename for the firmware mode the client is actually using (e.g. serving a legacy `.0` file to a UEFI client), the boot will fail or hang silently — this is one of the most common "PXE just doesn't work" root causes, so checking the client's firmware boot mode against the DHCP option 67 value is an early troubleshooting step.

### 10. How would you script a bulk power-cycle of a rack of servers using `ipmitool` or Redfish, and what would you check before doing it?

A simple loop reading BMC IPs from a file:

```bash
while read -r bmc_ip; do
  ipmitool -I lanplus -H "$bmc_ip" -U admin -P "$PASS" power cycle
done < bmc_ips.txt
```

Or via Redfish for a fleet with mixed vendors (more consistent across hardware):

```bash
while read -r bmc_ip; do
  curl -k -u admin:"$PASS" -X POST \
    "https://$bmc_ip/redfish/v1/Systems/1/Actions/ComputerSystem.Reset" \
    -H "Content-Type: application/json" -d '{"ResetType": "ForceRestart"}'
done < bmc_ips.txt
```

Before running: confirm which workloads are running on each host and whether they're drained/failed-over (a bulk power-cycle is disruptive), check current power/chassis status first rather than assuming every host is in the same state, stagger the cycle rather than hitting all servers simultaneously to avoid a thundering-herd effect on shared storage/network on boot, and have a rollback/skip list in case a subset of servers shouldn't be touched.

## Scenario Questions & Approach

### Scenario 1: "A newly racked server won't PXE boot at all — DHCP isn't even handing out an IP to it."

**Approach:** Confirm physical layer first — correct switch port, cable, and that the port is configured for the right VLAN (PXE VLAN vs data VLAN mismatch is common). Check the NIC is actually set to PXE boot in BIOS/UEFI boot order — some NICs have PXE disabled by default. Use `tcpdump` on the DHCP server (or a mirrored port) to see whether the DHCP discover packet is even arriving — if it's not arriving, it's a switching/VLAN/port issue; if it arrives but gets no response, it's a DHCP server-side or scope issue (exhausted pool, wrong subnet configured). Only after confirming the request is well-formed and reaching the server would I look at option 66/67 configuration.

### Scenario 2: "Half the servers in a rack came back up fine after a reimage; the other half are stuck at a black screen with no console output at all — even IPMI SOL shows nothing."

**Approach:** Since even SOL is blank, this points below the OS layer — likely a boot media/bootloader issue rather than an OS config issue (if it were OS-level, SOL would usually show at least some boot messages before hanging). Check via IPMI/Redfish sensor and SEL data first for hardware faults (memory, CPU) that could explain a hard hang pre-OS. Try mounting a known-good rescue ISO via virtual media and see if that boots — if the rescue ISO also fails to show anything, suspect a hardware issue (bad DIMM, failed boot drive) rather than the reimage process itself. If the rescue ISO boots fine, the problem is specific to the OS image/bootloader that was deployed, and I'd compare the failing servers' hardware profile against the working ones (different disk controller, different NIC needing a different driver in the install image, etc.).

### Scenario 3: "You're asked to migrate BMC management from flat/shared network access to a dedicated out-of-band management network, with zero downtime for production workloads."

**Approach:** This only touches the BMC's own network path, not the host OS's production NICs, so production traffic itself isn't directly at risk — but I'd still plan for the possibility of losing remote hands access mid-change. Stage the new out-of-band VLAN and switch ports first, and validate reachability to the BMC's new IP before cutting over DNS/inventory records, so there's a rollback path if the new path doesn't work. Migrate a small batch first (canary) and confirm IPMI/Redfish functionality (power control, SOL, sensor data) fully works over the new path before doing the rest of the fleet. Keep the old path available until the new one is confirmed working end-to-end, rather than cutting both at once, and document the new BMC IP ranges in whatever CMDB/inventory system is in use so future automation doesn't break.

### Scenario 4: "Firmware update pushed via Redfish to a batch of servers reports 'success' from the API, but several servers still show the old firmware version after reboot."

**Approach:** First distinguish "staged" vs "applied" — many Redfish/OEM update workflows (especially Dell's) stage the firmware and require a specific reboot type (or a second explicit apply step) to actually flash it, so an API "success" may only mean the payload was accepted, not that it was installed. Check the `UpdateService` task/job status endpoint rather than trusting the initial POST response, since firmware updates are often asynchronous. For the servers still on old firmware, check whether they actually rebooted after the update was staged, and check the SEL for any firmware-update-related failure events (checksum mismatch, insufficient power during flash, etc.). If it's a pattern affecting specific hardware batches, check whether those are on an older BMC firmware version that doesn't fully support the update workflow being used, since BMC firmware itself sometimes needs to be current before it will correctly apply component firmware.
