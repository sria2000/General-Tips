# Application Connectivity Troubleshooting Runbook

## Scenario

An application team reports that they are unable to connect to an application. The only information provided is an **IP address and port number**, for example:

```text
10.10.20.15:443
```

The objective is to systematically identify where the connectivity failure is occurring and determine whether the issue is related to **network connectivity, firewall rules, load balancers, SSL/TLS, the backend server, or the application itself**.

---

## 1. Confirm the IP Address and Port

First, validate the information provided by the application team.

```bash
ping 10.10.20.15
```

Check the routing path:

```bash
ip route
```

Trace the network path:

```bash
traceroute 10.10.20.15
```

If `traceroute` is unavailable:

```bash
tracepath 10.10.20.15
```

> **Note:** A failed `ping` does not necessarily indicate that the application is unreachable. ICMP may be blocked by a firewall while TCP connectivity is still working.

---

## 2. Test TCP Port Connectivity

Verify whether the specified port is reachable.

Using `nc`:

```bash
nc -zv 10.10.20.15 443
```

Using `telnet`:

```bash
telnet 10.10.20.15 443
```

For an HTTPS application:

```bash
curl -vk https://10.10.20.15
```

Typical results:

* **Connection succeeded** → Network path and TCP port are reachable.
* **Connection refused** → Host is reachable, but nothing is listening on the port or the connection is being actively rejected.
* **Connection timed out** → Possible firewall, routing, security group, or network issue.

---

## 3. Identify What the IP Address Represents

Determine what `10.10.20.15` actually points to.

The IP could belong to:

* Load Balancer (LB)
* Reverse Proxy
* Web Server
* Application Server
* Kubernetes Service
* Firewall/NAT address
* Direct backend server

This is important because troubleshooting a load balancer IP is different from troubleshooting a backend server IP.

Check the infrastructure or CMDB and verify:

```text
Client → Load Balancer → Backend Server → Application
```

---

## 4. Perform DNS Checks

If the application is normally accessed using a hostname, verify DNS resolution.

```bash
nslookup application.example.com
```

or:

```bash
dig application.example.com
```

Check:

* Does the hostname resolve?
* Does it resolve to the expected IP?
* Is the DNS record pointing to a load balancer?
* Are there multiple IP addresses?
* Is DNS resolution different from the expected environment?

For example:

```bash
dig +short application.example.com
```

---

## 5. Check SSL/TLS Connectivity

For HTTPS applications, verify the TLS handshake.

```bash
openssl s_client -connect 10.10.20.15:443
```

If the application requires a hostname/SNI:

```bash
openssl s_client -connect 10.10.20.15:443 -servername application.example.com
```

Check for:

* Successful TLS handshake
* Certificate validity
* Certificate expiry
* Certificate chain
* TLS protocol/version
* Cipher negotiation
* SNI-related issues

---

## 6. Test the HTTP/HTTPS Layer

Use `curl` to verify the application response.

```bash
curl -Iv https://10.10.20.15
```

If the application requires a hostname:

```bash
curl -Iv https://application.example.com
```

Useful HTTP status codes:

| Code    | Meaning                          |
| ------- | -------------------------------- |
| **2xx** | Successful request               |
| **3xx** | Redirection                      |
| **4xx** | Client/request-related error     |
| **5xx** | Server/application-related error |

For example:

```text
HTTP/1.1 200 OK
```

indicates that the request reached the HTTP service successfully.

A:

```text
HTTP/1.1 503 Service Unavailable
```

may indicate that the load balancer or application has no healthy backend servers.

---

## 7. Check Load Balancer Health

If the IP belongs to a load balancer, check the LB configuration and health status.

Verify:

* Virtual Server / VIP status
* Listener configuration
* Port 443 configuration
* Backend pool status
* Backend server health
* Health-check configuration
* SSL certificate configuration
* Connection errors
* Timeout settings
* Recent configuration changes

Check whether the load balancer considers the backend servers **UP/Healthy**.

Typical flow:

```text
Client
   |
   | TCP/443
   v
Load Balancer
   |
   | Backend connection
   v
Application Server
   |
   v
Application
```

If the LB is reachable but all backend servers are unhealthy, investigate the backend servers rather than the client-side network.

---

## 8. Check the Backend Server

If the load balancer forwards traffic to backend servers, connect to the relevant backend and verify that the application is listening on the expected port.

Using `ss`:

```bash
ss -tulnp
```

For a specific port:

```bash
ss -lntp | grep :443
```

Alternatively:

```bash
netstat -tulnp
```

Confirm:

* Is the application process running?
* Is it listening on the expected port?
* Is it listening on the correct IP/interface?
* Is it listening on `0.0.0.0` or only `127.0.0.1`?
* Is another process using the port?

---

## 9. Check the Application Service

Check the application service status.

For systemd-managed applications:

```bash
systemctl status <application-service>
```

Check recent service logs:

```bash
journalctl -u <application-service> --since "30 minutes ago"
```

Check running processes:

```bash
ps -ef | grep <application>
```

or:

```bash
ps -eaf
```

Look for:

* Service stopped
* Application crashes
* Startup failures
* Port binding errors
* Configuration errors
* Dependency failures
* Database connection failures

---

## 10. Check Firewall Configuration

Check whether the host firewall is blocking the required port.

For RHEL-based systems using `firewalld`:

```bash
firewall-cmd --list-all
```

Check the active zones:

```bash
firewall-cmd --get-active-zones
```

Check whether port 443 is allowed:

```bash
firewall-cmd --list-ports
```

For systems using iptables:

```bash
iptables -L -n -v
```

Also consider external network controls such as:

* Network firewall
* Security groups
* Network ACLs
* Cloud firewall rules
* Data-centre firewall policies

---

## 11. Check SELinux

On RHEL-based systems, verify SELinux status:

```bash
getenforce
```

Check for recent SELinux denials:

```bash
ausearch -m AVC -ts recent
```

or:

```bash
grep -i denied /var/log/audit/audit.log
```

If SELinux is enforcing, determine whether it is preventing the application from binding to or accessing the required resource.

> Do not disable SELinux as the first troubleshooting step. Identify and address the specific policy denial.

---

## 12. Check Application Logs

Review application and web-server logs for errors around the time of the reported failure.

Common locations include:

```text
/var/log/
```

Examples:

```bash
tail -f /var/log/messages
```

For nginx:

```bash
tail -f /var/log/nginx/error.log
```

For Apache:

```bash
tail -f /var/log/httpd/error_log
```

Look for:

* Connection errors
* Authentication failures
* SSL errors
* Backend connection failures
* Timeout errors
* Application exceptions
* Database connectivity issues

Always correlate the log timestamp with the time reported by the application team.

---

## 13. Check Server Resources

Determine whether resource exhaustion is affecting the application.

### CPU

```bash
top
```

or:

```bash
uptime
```

### Memory

```bash
free -m
```

### Disk Space

```bash
df -h
```

### Disk I/O

```bash
iostat -xz 1 5
```

### System Load

```bash
uptime
```

Look for:

* High CPU utilisation
* Memory exhaustion
* Swap usage
* High load average
* Disk space exhaustion
* High disk I/O wait
* File-system issues

---

## 14. Perform Packet Capture

If the issue is still unclear, use `tcpdump` to determine whether packets are reaching the server and whether responses are being returned.

For the specific host:

```bash
tcpdump -i any host 10.10.20.15
```

For HTTPS traffic:

```bash
tcpdump -i any host 10.10.20.15 and port 443
```

For TCP SYN packets:

```bash
tcpdump -i any 'host 10.10.20.15 and tcp[tcpflags] & tcp-syn != 0'
```

Look for the TCP handshake:

```text
Client → SYN → Server
Client ← SYN/ACK ← Server
Client → ACK → Server
```

If you see:

```text
SYN → 
SYN →
SYN →
```

with no response, investigate network/firewall/routing issues.

If you see:

```text
SYN → SYN/ACK → ACK
```

then TCP connectivity is established and the investigation should move up the stack.

---

## 15. Check Load Balancer and Network Errors

If a load balancer is involved, review its logs and metrics.

Look for:

* Backend connection failures
* Backend timeouts
* Health-check failures
* Connection resets
* SSL handshake failures
* HTTP 4xx/5xx responses
* Pool/member failures
* Excessive connection counts
* Traffic spikes

Correlate the LB logs with the application server logs to determine where the request is failing.

---

# Troubleshooting Decision Flow

A practical troubleshooting sequence is:

```text
Application Team Reports Failure
              |
              v
     Confirm IP + Port
              |
              v
       Test Network Path
       ping / traceroute
              |
              v
       Test TCP Port
          nc / telnet
              |
              v
      Identify IP Owner
     LB / Proxy / Server
              |
              v
       DNS Verification
        dig / nslookup
              |
              v
       SSL/TLS Testing
       openssl / curl
              |
              v
      Is it a Load Balancer?
          /          \
        Yes           No
         |             |
         v             v
   Check LB Health   Check Server
   Backend Pool      Listening Port
         |             |
         v             v
    Backend Server → Application
              |
              v
       Check Firewall
              |
              v
        Check SELinux
              |
              v
       Check App Logs
              |
              v
     Check CPU / Memory
       / Disk / I/O
              |
              v
       Packet Capture
         tcpdump
              |
              v
     Identify Root Cause
```

# Key Troubleshooting Principle

Always troubleshoot **from the bottom of the stack upwards**:

```text
Network
   ↓
TCP Port
   ↓
Load Balancer / Proxy
   ↓
TLS/SSL
   ↓
Web Server
   ↓
Application Process
   ↓
Application Logs
   ↓
Dependencies
   ↓
Database / External Services
```

The key objective is not simply to determine that the application is "down", but to identify **exactly where the communication path is breaking** and provide evidence for the root cause.
